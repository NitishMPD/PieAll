# PieAll
Author: Nitish


## Browser screenshot actions - 23 October 2026

Default browser rings replace Paste plain text and Search actions with two direct actions: Capture current (the visible page copied to the clipboard) and Capture full page. Downloads, Copy URL, Reopen closed tab, New private window and Window remain. Other apps retain Search actions; slash search remains available, and saved custom layouts remain authoritative. Both capture actions are also available to customization and the dashboard app list, subject to native eligibility.

Screenshot actions never open DevTools. Capture current reads the largest visible accessible page document's bounds, excluding documents named DevTools/Developer Tools, clips them to the source browser client area, captures those screen pixels through Windows GDI and publishes an opaque clipboard image. Dimensions are limited to 16384 pixels per side and 16 megapixels total. Missing page bounds fail explicitly rather than capturing the entire desktop. This is a visible-screen capture: topmost overlays can appear, protected surfaces may be blank, and minimized or offscreen content is not reconstructed. The current image intentionally replaces clipboard content; it is not pasted automatically or saved as a file.

Capture full page uses each browser's native path without DevTools or an extension. Edge and Firefox-family profiles send Ctrl+Shift+S, invoke the English Capture full page / Save full page button and leave the browser preview open for Copy/Save. Chrome and other Chromium profiles use the page document's Windows UI Automation Scroll pattern, take overlapping Windows screen captures from top to bottom and stitch them at the midpoint of each overlap. The starting vertical scroll position is restored before publication; restoration is attempted after errors and focus loss too, and never targets a replacement document. A changed or closed page can prevent restoration. Horizontal-overflow pages and pages without native scrolling information fail explicitly.

Chrome-style captures are staged as raw rows in an anonymous temporary file, bounded to 256 megapixels, 262144 pixels in height, 16384 pixels in width, 512 frames and a 180-second capture deadline. Small completed results (at most 32 megapixels and 32768 pixels tall) are copied to the clipboard. Larger results stream to PNG in the Windows Downloads folder under PieAll Screenshots, using collision-safe names; the toast and dashboard result report the saved path. Large export preserves the clipboard. Native pixel buffers and PNG encoding are bounded to viewport/row memory instead of allocating an entire large output image. Raw staging can require up to about 1 GiB of disk space, plus the encoded PNG. The temporary and unpublished output files are removed when the operation ends or fails normally.

The input lease stays with capture. Held keys/buttons (including Escape), focus loss, a replacement document, viewport changes, changed page height and scrolling deadlines stop capture without publishing an incomplete result. Each scroll waits for its position to settle; screenshot positions are read back before stitching. Midpoint overlap reduces repeated small fixed headers/footers, but large sticky elements, animation, topmost overlays and content loading after the capture can still cause artifacts. No page styles or scripts are injected. Existing DevTools/device-emulation settings are not changed or closed. Chromium capture does not depend on English control names; the Edge/Firefox overlay path does.

Rust all-target checks and regression tests cover bounded dimensions, clipping, negative monitor coordinates, long-page planning, overlap stitching, PNG RGB ordering, truncated encoder input and browser menu availability. Native pixel output, scroll restoration, cancellation, dynamic pages, DPI, browser variants and clipboard behavior remain user-run acceptance checks. The desktop inspection helper was unavailable; no app was launched by the agent.


## In-app action notices - 22 October 2026

Dashboard jobs appear as dismissible toast notifications instead of a persistent bottom list. Their native job IDs, per-job Cancel, saved download location and lazy result reports are preserved. Dismissal is local to the current dashboard session and never cancels work. Notifications persist until closed or pruned from native history. While the dashboard is active, all job notices, including saved downloads, suppress the separate floating window to avoid duplicates. Background desktop notices retain their existing behavior.

## Parallel actions - 21 October 2026

The default Tauri shell runs independent jobs concurrently. Downloads, media processing and local file actions no longer hold the app-wide interactive lease for their full lifetime. Each accepted job owns its captured paths/text, parameters, download preferences/destination, cancellation token, progress, output location and result. New selections, ring invocations and actions remain available during background work. The dashboard keeps every active job plus a bounded recent history (completed history is pruned to fewer than 20 entries when another job starts); full reports load on demand rather than travelling with every progress refresh.

Only foreground input and clipboard exchanges remain mutually exclusive: capture, browser address copying, app shortcuts, clipboard writes and window actions. Downloads release that lease immediately after capturing their URL, before tool setup or networking. Slow report/text work also runs in the background; automatic copy/paste occurs only when the original selection revision is still current and the input lease is available. Otherwise its result remains in Jobs, without overwriting newer input. Closing a notification dismisses only that job's notices. Cancellation, completion, dismissal and Open location resolve by job ID, independently of the current selection or latest job.

Shared engine setup is serialized with cancellable waiting and reloads the current engine records after acquiring its gate, so concurrent jobs reuse installed tools. The gate is released before execution; custom engine configuration refuses changes during setup and running jobs retain their engine snapshot. Update checks/downloads have their own operation state and allow ordinary work alongside them. Exit and installer handoff still require all work to finish or be cancelled. Worker time/memory/output limits and collision-safe publication apply per job. The opt-in historical GDI shell retains its original one-job behavior.

Regression coverage checks independent cancellation, selection changes during work, out-of-order completion, retained output paths/dismissal, cancellable setup waiting and per-job dashboard controls. Native overlapping downloads, foreground/clipboard behavior, toast interaction and accessibility remain user-run acceptance checks; no app launch or packaging build was performed.


ZIP extraction and integrity testing report expanded-byte progress through the existing worker channel, retaining the selected-archive count for batch jobs. Streaming checks cancellation every 64 KiB and limits progress updates to about ten per second; successful processing also reports completion, including empty archives. Existing declared-size validation, staging and publication guards remain in force.

ZIP listing, integrity testing and extraction allow up to 1536 MiB of ZIP input and total expanded data, 768 MiB per expanded file and a 3000:1 expansion ratio (with the existing 1 MiB allowance). These size and ratio limits are three times their original values; entry count, ZIP creation limits and safe extraction rules remain unchanged.

## Browser downloads - 21 October 2026

The hold hook passes a confirmed hold's physical key release through to Windows, including when shortcuts are disabled during the hold. This clears asynchronous key state before the shared shortcut dispatcher checks for held input; repeat key-downs remain intercepted. Browser URL copying and app shortcuts retain their held-key, foreground and process checks.

Text capture reserves its clipboard activity before its worker is scheduled, so fast ring actions wait for queued as well as running captures. Cancellation is checked before hold confirmation and before selection-copy input; choosing Copy URL or Download during a fast release cannot start a cancelled selection probe after the action has already begun. The shared three-chord URL sequence retains its two 70 ms inter-chord gaps.

Browser downloads in the sidebar accepts one explicit HTTP(S) video/post URL. Download video defaults to best available separate video plus audio, with a combined-stream fallback, no resolution cap and MKV merging/remuxing without forced re-encoding. Download audio extracts the best available audio; Original preserves its codec where supported, while MP3/M4A/Opus/FLAC/WAV are explicit conversions. Persistent defaults cover a quality cap, MKV/MP4/WebM container, audio format and a native-picked destination (initially the Windows Downloads folder). The visible form can override one job; Save as defaults persists its choices. Incompatible codecs/container combinations fail rather than silently selecting lower quality. Cookie-based login, DRM, live-stream acceptance, batch links and full playlists are not supported by this slice.

The native browser ring offers Download video and Download audio in Chromium and Firefox profiles. After selection capture stops and focus returns to the captured HWND/PID, PieAll sends the bundled Ctrl+L / Ctrl+C / Escape sequence, requires a fresh clipboard value owned by that browser process, restores the borrowed clipboard only if unchanged, and validates the HTTP(S) URL. Focus/source/input changes stop dispatch. The copied URL is immutable before tool setup or networking starts. A feed uses its current page address: open the exact video/post first. Pasted URLs remain available. No extension, native messaging host, browser registration or bridge is used.

Missing media engines set up automatically inside the job's serialized setup stage. Native-only sources are BtbN FFmpeg-Builds (win64 GPL build, including the H.264 encoder), yt-dlp and Deno GitHub releases. The HTTPS clients explicitly select the compiled native TLS provider (Windows Schannel); enabling native-tls alone does not change ureq's default Rustls provider. Setup requires HTTPS, the expected owner/repository/asset, a publisher-provided SHA-256 digest and exact bounded size. Digest verification checks the release bytes; it is not an independent publisher signature. Downloads and extraction are bounded and cancellable, all archive files/notices are retained, and release provenance is stored alongside each managed package. Private staged directories are removed on failure; engine records commit together after all required packages verify. Setup shares the existing reqwest/Tokio stack with the desktop: release metadata has a 30-second deadline, archives allow 15 minutes overall and a 30-second read-stall limit. Cancellation is checked every 100 ms while awaiting network operations, dropping the connection on cancel. Winget is not required; setup stays app-local and retains verified release assets and atomic engine records. Existing custom engines are preserved; an incomplete custom FFmpeg pair uses its sibling or asks for a complete pair in Advanced. Managed setup currently supports Windows x64.

Tool setup provides optional preinstallation of all tools; first use handles setup without visiting Settings. Advanced retains native file selection and pinned hashes. Downloads require FFmpeg and FFprobe from the same directory. Downloader configuration/plugins/cache, automatic runtime discovery and remote component fetching remain disabled; Deno runs bundled yt-dlp challenges. Downloads share hidden engine execution, worker containment, cancellation and collision-safe publication with local media jobs. A job allows one hour and a 2 GiB aggregate engine-output budget; staging final publication needs additional disk space. Files never open automatically. Automatic engine updates, real-site downloads and live setup acceptance remain unverified.

A per-job loopback HTTP/CONNECT proxy resolves each destination and connects to the checked numeric address. HTTP(S) targets use standard ports, no embedded credentials, and public addresses only, including redirect/extractor connections that use this proxy. Headers, connection count and timeouts are bounded; proxy sockets close with the job. This is a network guard for configured downloader requests, not an OS network sandbox for user-selected executables or their DLLs. No external network downloader is selected; FFmpeg post-processing inputs are restricted to file/pipe protocols.

Accepted proxy sockets explicitly use blocking mode before header reads and tunnel forwarding; Windows inherits the nonblocking listener mode otherwise, causing premature connection resets. A delayed-header regression covers this boundary. A metadata-only yt-dlp check against YouTube video T2Zp8NGdvrk failed through the proxy before the fix and succeeded afterward; this does not verify a complete download, Deno challenges or FFmpeg merging.

Engine-output scans tolerate temporary fragments disappearing during downloader renames/removal. Each remaining entry must be a regular file without Windows reparse attributes; file-count and aggregate size limits still apply. Inspection failures report their cause separately from an actual 2 GiB limit violation. Regression tests cover concurrent renames, inspection failures and the size limit; the reported repeat-download failure on X has not been verified against its source post.

Native current-page URL copying is implemented for Chromium and Firefox browser profiles. Feed/media disambiguation, canonical-post discovery from blob players, multi-video pickers, web-image saving and boards remain unfinished. An exact video/post page is the reliable feed target. Live engine installation, packaged worker dispatch, real yt-dlp/Deno/FFmpeg combinations, site behavior, focus/clipboard restoration, toast interaction and accessibility require user-run acceptance; static checks do not establish them.

## Implemented tool expansion ? 21 October 2026

This section supersedes earlier statements that cancellation, engine configuration and all document/media tools are outside the implemented slice. The registry now has 68 commands: the original 44, seven PDF commands, 15 media commands and two URL download commands. These command counts do not measure completion of the distinct product-plan workflows.

Jobs report actual processed-target counts and, when duration is known, FFmpeg encoding progress for the current file. Native job IDs bind cancellation and dismissal to the correct operation. Close hides that job's notification, including its later completion notice, without stopping work or suppressing clipboard/paste results. Cancel requests cooperative cleanup; completed outputs remain. After five seconds an unresponsive worker and its descendants are terminated. Images-to-PDF exposes A4/Letter/image-sized pages, portrait/landscape orientation, 0?144 point margins and JPEG quality. Page order still follows native selection order; there is no page organizer.

The bundled MIT-licensed lopdf parser powers PDF inspection, page extraction, per-page splitting, rotation, stream compression, document metadata removal and selectable-text export. Inputs are limited to 64 MiB and 500 pages; splitting emits at most 100 files, rewritten PDFs at most 128 MiB and text at most 8 MiB. Page ranges accept `all` or ascending ranges such as `1-3,5`, deduplicated in document order. Rewriting refuses forms and signed PDFs; password entry is not implemented. Rotation respects inherited page rotation. Compression preserves existing encoded image streams and saves no output if it would be larger. Metadata removal clears Info/Metadata references; it is not sanitization. Extraction is not secure redaction, and text export is not OCR or layout reconstruction. Active content, bookmarks and links are not comprehensively rewritten or validated.

Fifteen optional media commands cover video conversion, compression, resize, rotation, mute, trim, GIF export, frame extraction and audio extraction; audio conversion, trim, MP3 compression, single-pass loudness normalization and volume adjustment; and media inspection. Supported input containers are MP4/M4V/MOV/MKV/WebM/AVI/WMV and MP3/WAV/FLAC/M4A/Ogg/Opus/AAC/WMA. Output choices depend on installed codecs. Video conversion uses H.264/AAC or VP9/Opus, the first video and optional first audio stream, and re-encodes; additional tracks/subtitles are not copied. Audio normalization targets ?16 LUFS, ?1.5 dB true peak and LRA 11 in one pass. Numeric parameters and output formats are validated; arbitrary codec/filter arguments are not accepted. Non-media local jobs retain 120 seconds; media jobs allow one hour, 8 GiB inputs and 2 GiB outputs. Unknown-duration sources show encoded time and file counts without a guessed percentage. Progress can estimate encoding completion before final muxing/copy/publication finishes.

Tool setup owns automatic first-use dependencies and Advanced custom paths. Canonical paths and SHA-256 fingerprints live in the existing versioned SQLite store (`settings.sqlite3`, schema 3; engine records survive migration, and the historical browser tables are unused). Changed custom executables must be selected again. Engine files are held against replacement during validation/execution. PieAll does not search PATH/current-directory executables or independently certify custom binaries/DLLs. Fixed demuxers and file/pipe-only input protocols constrain local media jobs. Engines run hidden with bounded pipe collection, process-tree cancellation and safe staging. Real-distribution execution remains a manual acceptance gate.

ZIP creation now includes selected folders, nested/empty directories and selected files, with Deflate level 0?9 or Store. It preflights names, links, depth (64), count (10000) and source bytes (512 MiB), rejects duplicate archive paths and never includes its own staged output. Cancellation is checked during traversal and streaming. ZIP outputs retain the existing no-replace publication policy.

Exact in-feed media targeting, web-image saving, boards/Library, automatic engine updating, PDF page thumbnails/merge/reordering/annotation/redaction/OCR, rich image layers/masks, media timelines/waveforms/recording and the remaining expanded catalog are still planned. The 72-workflow inventory remains in section 13 of PieAll-plan.md. Type checks and unit tests do not establish native toast hit testing, accessibility, packaged worker dispatch or real-codec acceptance.

## Invocation model — 20 October 2026

PieAll is a tray utility, not an import app. The dashboard no longer opens at launch; it stays reachable from the tray as the full action list, the parameter editors and the accessible route.

- **Hold `** anywhere in Windows. A low-level keyboard hook (src-tauri/src/hold.rs) holds back each unmodified backtick press and opens the ring at the cursor on key-down, in every app. A release within 150 ms, or another key pressed first, counts as typing: the ring vanishes at once (no fade) and the backtick is replayed in order, so typing still works at the cost of a brief flash. Text capture (Ctrl+C) waits until the hold passes 150 ms, so a typed backtick never sends Ctrl+C, and a refused open (PieAll busy) is only reported once the hold is confirmed. Over apps whose shortcut profile never reads text (Figma, Explorer and the desktop, Adobe apps; terminals excluded because shells use ` as an escape), the hold is confirmed immediately and a plain ` is never typed there, like AutoHotPie. While held, the ring never takes focus: the app keeps it, shortcuts and results land without a focus round-trip, and the hook takes Escape to cancel. The ring is placed and sized with native calls only (no Tauri main-thread hops), and the release position is read natively. Once open, releasing the key always ends the ring: it runs the highlighted action slice (falling back to the cursor's direction when nothing is highlighted, e.g. after a flick past the rim), and anything else (center, nothing, a submenu slice, or a busy session) closes it. Submenus open only by resting 550 ms on their slice. As a backstop, the native side closes the ring itself 400 ms after the release (after any selection capture finishes) if it is still the same ring, so a stalled web round-trip or a failed run cannot leave it open. While ` is held, focus loss never closes the ring; otherwise only the ring that actually gained focus closes on focus loss (late focus-loss events from a hidden ring are ignored), and a ring that closed is never re-focused. Clicking a slice while still holding ` runs it; app shortcuts wait up to 5 s for the key to come up before sending. Shift (~), Ctrl, Alt, AltGr and Win combinations and injected input pass through. Ctrl+` and the tray open the same ring without the hold gesture. Pressing either again while the ring is open closes it.
- **Context comes from the foreground window**, captured before PieAll shows anything:
  - Explorer or the desktop: the selected items, read over COM. With Windows 11 tabs, only the active tab's visible view counts. With nothing selected, the open folder itself is the target.
  - Any other app except terminals: the selected text, copied with an injected Ctrl+C. The user's clipboard is snapshotted first (memory-backed formats, up to 64 MiB) and restored straight after; no clipboard change within 300 ms means no selection. Running an app shortcut or window action cancels an unfinished read: the read stops waiting, restores the clipboard, and the action's keys are sent only after that (bounded at 1 s), so they never interleave with the Ctrl+C. Terminal classes never get Ctrl+C because it interrupts there.
  - Otherwise: that app's window (center, pin on top, fill screen, info).
- **Slices are presets that run in place, with no editors.** web/menus.ts defines them per context, and the native registry filters what's eligible. Empty submenus disappear, a single-choice submenu collapses into its choice, a lone file-type submenu (PDF tools, Media tools) is flattened onto the ring, and anything past eight slices moves into More. Images: Compress 50%, Half size, Convert (PNG/JPG/WebP), Rotate (right, left, flip across, flip down), Copy image, Remove info, Make PDF, More. Files: Copy path, Zip, Extract here, Duplicate, Terminal here, Copy SHA-256, Folder size, Find duplicates, List/Test ZIP. Text: UPPERCASE, lowercase, Title Case, Trim, Sort, Unique lines, Format JSON, More (minify, URL and Base64 encode/decode, count).
- **Results stay where the user is.** File outputs publish beside the original under a smart name. Text results are pasted over the selection, then the user's clipboard is restored after 400 ms; if focus moved, the result stays on the clipboard and a toast says to press Ctrl+V. Reports (SHA-256, details, colors, folder size, duplicates, ZIP listing, window info, count) go to the clipboard. A small nonactivating notice confirms outcomes in the bottom-right work-area corner, with a 16-DIP inset above the taskbar. It uses the invocation monitor and stays there for that job, without following the cursor. Job notices are hidden while the dashboard is foreground; progress and Cancel remain in its footer, including completion/error status. Returning to the dashboard hides an existing job notice without dismissing the job.
- **Smart names** (src/output.rs `output_stem`): `<stem>-<tag>.<ext>`, with tags compressed, rotated, flipped, clean, cropped, framed, grayscale, contact-sheet, or the new `<w>x<h>` after a resize. Re-applying the same tag replaces it instead of stacking it (photo-compressed (2) compressed again gives photo-compressed). Convert keeps the stem and changes the extension. Duplicate gives `<stem> - Copy`. Zip uses the item's name, or the folder's name for several items. Extract and Make PDF use the source stem. Collisions add Windows-style ` (2)` counters; nothing is ever replaced.
- **Image edits keep the source format** (JPEG re-encodes at quality 92). Compress writes JPEG at the chosen quality unless the image has real transparency, which stays as maximally compressed PNG. A compression that would not shrink the file saves nothing and says so. Resize accepts `scale` (1–100%) as well as maximum width/height.

Known limits: holding ` can no longer auto-repeat backticks; there is no setting yet to turn the hold gesture off or rebind it; text capture assumes the app's Ctrl+C/Ctrl+V; non-memory clipboard formats (GDI bitmaps, metafiles) are regenerated by Windows from their DIB/EMF siblings or lost; fullscreen games receive the ring like any app. Elevated windows ignore input from a non-elevated PieAll.

## Current architecture — 20 October 2026

PieAll now uses Tauri 2, React/TypeScript and its existing Rust execution core. The port stays in this repository; Captrain is an architecture reference and is unchanged. This section and docs/tauri-port.md supersede the historical baseline below. The original GDI shell is available only through the explicit legacy-ui feature; do not run both shells together.

Rust owns immutable contexts, revision/ticket rejection, source HWND/PID, registry eligibility, editor ownership, foreground-input coordination and independent job results. The frontend cannot supply arbitrary file paths or override captured window identity. Native opening/dropping replaces context; clipboard text remains explicit. Worker dispatch precedes Tauri initialization. Launcher actions (Terminal here, Reveal) run in the app process, not the worker: the worker's job object kills every descendant on exit and a child holding its pipes stalls the reply. Terminal starts cmd.exe through ShellExecute, which gives it a new console of its own and never PieAll's stdio (SEE_MASK_NO_CONSOLE would do the opposite and attach it to PieAll's console). Existing output/ZIP guards, 120-second jobs, 1.2-second capture helper and 512 KiB per-job results are retained; background jobs run independently. Previews are serialized off the UI thread, bounded to 64 MiB input/128 MiB allocation/16384-pixel dimensions, normalized for orientation and reduced to 320px.

The shell owns tray, fixed Ctrl+backtick invocation, foreground capture before focus, close-to-hide dashboard and single-instance forwarding of file arguments. Dashboard Show ring preserves explicit context. Exit/install refuse active operations or editors. Native focus, circular hit regions and mixed DPI remain acceptance gates.

The Cargo workspace defaults to pieall-desktop; one root Cargo.lock and one pnpm lockfile are used. Windows x64 NSIS packaging is per-user and uses system WebView2 instead of bundling a browser. Release Rust settings favor size. Smaller artifacts, lower process-tree memory and latency remain unmeasured goals.

The Tauri shell replaces the old custom updater protocol with Tauri signed updates. Configured releases check the PieAll GitHub feed after 10 seconds/every six hours; debug/unconfigured builds never check. Notes/progress, explicit download and separate install confirmation are implemented. Stable owned URLs, HTTPS, ten-minute/256 MiB download limits and installer/signed-version verification apply. Installer bytes remain bounded in memory until install/exit. Native input leases exclude conflicting capture/editor/input exchanges; updater checks and downloads keep their own state, and installation requires idle workers. Versioning, signed installer/portable packaging, offline verification and draft-first CI are implemented in docs/releases.md. New drafts are validated from the creation response rather than an immediately refreshed release list; expected tag, draft state and exact source commit remain mandatory. Keys, optional Authenticode and clean-Windows/live release validation remain external; Captrain's key is not reused. No analytics is implemented.

Formatting, TypeScript, static rendering and targeted tests are agent-run; builds/dev servers/app launches remain user-run. The workspace all-target Rust check and strict Clippy now pass; native installer/UI acceptance remains user-run. Do not infer native accessibility, focus, transparency, Explorer correctness, DPI or performance from source checks. The current UI uses SVG/local icons and alpha fills, with no native backdrop blur. Browser/engine/collection/configuration/cancellation/public-hub milestones remain outside the implemented slice.

See docs/tauri-port.md for architecture, signing and commands; verification.md for actual check results. Exact pre-port docs are preserved in docs/native-baseline-project.md and docs/native-baseline-design.md.

## Historical native baseline (legacy-ui only)

The following records the original implementation. Its no-network/GDI boundaries do not describe the default Tauri shell.

PieAll is a Windows 11 x64 local radial action utility. The full product vision remains in PieAll-plan.md. This first implementation prioritizes a real native invocation surface and working local image, file, ZIP, text and window tools. ## Runtime and ownership
The UI captures an explicit immutable selection before opening. Explicit dropped/opened files replace the prior context. Clipboard text requires an explicit user gesture. The registry owns all-target eligibility; handlers validate again. Expensive handlers execute in a temporary child process so codecs do not stay resident. Native UI owns presentation and source focus.

Outputs preserve original files, stage beside the destination and publish using atomic no-replace hard-link creation. Symlink/reparse inputs and destination parents are rejected; output names are controlled by the application. ZIP extraction uses a new private staging directory, validates paths, rejects links and applies quotas before publishing a new sibling folder. No existing directory is merged. Input byte/pixel/count limits protect workers. No network requests or analytics are implemented.

## First-slice boundaries
Native Win32 and opaque warm GDI rendering are a provisional implementation; Direct2D/translucency, full custom UI Automation, modifier-drag OLE support, automatic active-tab browser capture, persistent configuration/SQLite, cancellation and production packaging have not passed their planned gates. Explorer selection fails closed when foreground tab identity is ambiguous. Explicit file opening/dropping is the reliable fallback. No claims of measured performance or full 100-action coverage.

## Download completion location - 21 October 2026

Explorer receives its selection switch separately from the saved path, preserving filenames with spaces, commas and Unicode. Open location uses the actual completed output's folder (Windows Downloads or the chosen custom destination), even if defaults change afterward.

Successful video/audio downloads expose Open location in their completion toast, including while the dashboard is active. The action uses the completed job ID and its native saved output path to reveal the file in Explorer; web parameters cannot supply a path. Failed, cancelled and running downloads expose no location action. Completion toasts with an output stay eight seconds and can be closed. Files never open automatically.
